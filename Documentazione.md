# DESCRIZIONE DETTAGLIATA DEI FILE

## Qui descriverò in maniera più o meno dettagliata quello che è presente nei file scritti fino a questo momento, aggiungendo man mano i nuovi script per avere alla fine una documentazione di quanto fatto:

### BACKEND

- `index.js`: Punto iniziale del progetto, dove si inizializza e si "starta" il server. All'interno troviamo infatti le varie funzioni importate dalle dipendenze e librerie scaricate, come `createServer` da http, `Server` da socket.io.
  La funzione principale del file è `startServer`, una funzione async (asincrona, così da non bloccare l'intera applicazione su questa funzione, dal momento che all'interno utilizziamo le `await`, che potrebbero rallentare il flusso della funzione ) nella quale troviamo: - la chiamata alla funzione `connectDB`, definita nel file `./config/database.js`, che chiama MongoDB per istanziare una connessione con questo ultimo - chiamiamo la funzione importata prima `createServer` per generare il nostro server http, e alla funzione diamo come parametro la nostra applicazione Express, così da avere tutto collegato con quello fatto prima. - dal nostro http server creiamo il nostro canale `io`, definendo anche quello che è il `cors`: strumento necessario per far rispondere il nostro server a chiamate che arrivano da destinazioni diverse da quella dove si trova il server- - `app.set("io", io)` ci permette di salvare all'interno dello spazio globale della mia applicazione express il canale di comunicazione (la socket) io, così da poter essere utilizzata da tutte le componenti. - chiamiamo la funzione `io.use(verifySocketToken)`, funzione fondamentale che ha il ruolo di middleware, cioè quello di autenticare tramite il JWT il canale, rendendolo sicuro e "privato" da chi non possiede il token. Passiamo infatti la funzione verifySocketToken come callback (non passiamo la funzione con le parentesi tonde), non viene eseguita subito, ma verrà eseguita quando un utente utilizzerà la chiamata io(...path server) per collegarsi alla socket. E' come se stessimo scrivendo una regola da applicare nella comunicazione con il canale io. - adesso chiamiamo la funzione io.on(), che ci permette di metterci in ascolto su determinati eventi che passano nel nostro canale. Uno di questi è l'evento `connection`, che scatta quando, nel file `GameRoom.tsx`, chiamiamo la funzione io(path del server), che è proprio il comando per collegarsi alla nostra web socket. - dopo l'evento connection stiamo in ascolto sulla nostra socket di altri eventi, come ad esempio: `join_lobby_rooms`, che fa si che un utente riceva un messaggio se un altro utente si collega alla stessa lobby/rooms. Infatti sulla socket mandiamo un messaggio tramite la funzione `emit`, che mandiamo però solo agli utenti connessi alla stessa `room`. Stiamo in ascolto anche su eventi come `disconnect, error`. - infine diciamo al nostro server http di stare in ascolto per ricevere tutte queste comunicazioni sulla porta definita nel file `.env` tramite la funzione `listen()`. - ultima riga del codice è la chiamata proprio alla funzione appena descritta, per fa partire il tutto
- `app.js`: File in cui istanziamo la nostra applicazione Express per creare il nostro server (che come abbiamo detto prima poi verrà legato con http per utilizzare le socket). - Importiamo sia la libreria `express` e sia la libreria `cors`. Istanziamo la nostra app facendo `app = express()` e tramite le funzioni `use` applichiamo delle regole alla nostra applicazione, come quella `cors()` e `express.json()` che da al nostro server la possibilità di comunicare tramite strutture json. In questo file importiamo anche le funzioni di `router` userRouter e lobbyRouter, che verranno chiamate in base all'url specifico della chiamata della api al nostro server express. Infatti subito dopo troviamo le funzioni use() nella quale troviamo i path delle chiamate api che vengono gestite in maniera diversa dalle rispettive funzioni di router. Importante notare la configurazione del cors: nel campo `origin` infatti stiamo dicendo che le comunicazioni sicure sono solo quelle che provengono da localhost:5713, che è proprio la nostra porta nella quale, per ora, hostiamo il nostro frontend
- `token.js`: Funzione semplicissima che, importando tutto dalla libreria jsonwebtoken, crea un accessToken firmato tramite la funzione `sign` e che lega al JWT creato anche l'id dell'utente che si è appena loggato dentro il nostro server, così da avere il riferimento univoco all'utente in questione. La firma viene fatta chiamando dal nostro file `.env` la password segreta per la creazione del token. Analogamente creiamo anche un refreshToken, che sarà utilizzato dal client, salvato in un cookie http, per richiedere un nuovo accessToken
- `routes`: dentro questa cartella troviamo i file che gestiscono il routing delle chiamate, cioè si occupa di definire le route (le url) delle diverse chiamate API e per ognuna di queste chiamata il giusto controllor. Per fare ciò viene utilizzato l'oggetto `router` importato grazie alla libreria express. Inoltre alcune di queste chiamate vengono anche "protette" da delle funzioni chiamate middleware che si instaurano durante la comunicazione per verificare l'autenticità dell'utente tramite i token generati in precedenza. - `user.router.js`: in questo file ci occupiamo del routing delle chiamate API che riguardano le azioni di login, register e logout. Per ognuna di queste azioni definiamo una route differente, per esempio `router.route("/login").post(loginUser)` definisce la route che deve avere l'api per il login dell'utente e chiama la funzione corretta all'interno del controller che definisce il flow da seguire. Nota importante da fare è sulla route che definisce la chiamata API utilizzata quando un accessToken scade e viene richiesto il rilascio di un nuovo token tramite la chiamata API refresh alla quale viene passato il refreshToken. - `lobby.router.js`: in questo file invece stabiliamo il routing per le chiamate API che interessano invece l'interazione con le lobby. Notiamo però subito una cosa differente: nella definizione della route troviamo infatti un secondo paramentro, il `verifyToken`. Questa funzione, come quella descritta in index.js, verifySocketToken, controlla la validità del token JWT utilizzato per autenticare la richiesta da parte dell'utente. Il token viene creato subito dopo il login, e questo verrà salvato dal client che lo utilizzerà per le successive comunicazioni con il server, così da rendere la comunicazione sicura e autenticata (esempio di routing: `router.route("/join/:id").post(verifyToken, joinLobby)`)
- `middleware`s: in questa cartella troviamo le funzioni, già citate nelle descrizioni precedenti, che intervengono da "buttafuori" per autenticare le comunicazioni tramite il controllo del JWT. - `verifyToken`: Questa funzione controlla il token utilizzato nelle API REST classiche. La funzione prende in input `(req, res, next)`: l'oggetto next è una funzione che viene chiamata far continuare il flow con la prossima azione da eseguire nel caso in cui la verifica del token sia andata a buon fine. Dalla req spacchettiamo il token, che abbiamo mandato nell'header di quest'ultima con il formato `Bearer + stringa che rappresenta il token`. Una volta ottenuto il token chiamiamo la funzione `verify`, importata dalla libreria jsonwebtoken. Se la verifica va a buon fine attacchiamo alla richiesta un nuovo elemento, `req.user = verified` così da poter controllare successivamente, ad esempio dal controller, se l'autenticazione è andata a buon fine e anche per poter accedere all'id dell'utente. - `verifySocketToken`: Funzione del tutto analoga a quella precedente che serve però per autenticare la comunicazione sul canale socket. In questo caso aggiungiamo però tutti i controlli per essere sicuri di prendere il token: controlliamo infatti che sia presente direttamente come token o che sia presente nell'header della socket. A quel punto controlliamo se è stato mandato direttamente o come nel formato precedente, quindi come Bearer Request. Alla socket aggiungiamo quindi il nuovo campo `socket.user = verified` per poter accedere sempre alla verifica del token (fatta nello stesso modo con la funzione verify)
- `user.model.js e user.controller.js`: analizziamo contemporaneamente questi due file. Nel primo file, che si trova all'interno della cartella `module`, stiamo definendo il modello, lo `Schema`, la struttura, che i dati relativi per ogni utenti devono avere all'interno del mio DB. Questo ci permette di conoscerla, cosa fondamentale per recuperare le informazioni salvate all'interno di questo strutture. Nel secondo file invece, che si trova nella cartella `controllers`, vengono definite le funzioni che gestiscono il flow delle azioni da compiere per la registrazione, il login e il logout dell'utente. Queste funzioni devono in primo luogo comunicare con il DB, cosa che facciamo in maniera semplice grazie alla libreria `mongoose`, che ci permette di utilizzare delle semplici funzioni al posto di grezze e complesse query. Analizziamo adesso nel dettaglio i file: - `user.model.js`: abbiamo detto che qui troviamo la definizione dello schema dei dati relativi al nostro utente nel nostro DB. Inoltre abbiamo anche importato sia la libreria mongoose che anche la libreria `bcrypt`, che ci servirà per crittare le password per non salvare in chiaro nel nostro DB. Per definire il nostro `userSchema` chiamiamo proprio `new Schema({})`, all'interno del quale definiamo le chiavi che il nostro modello deve avere con le rispettive caratteristiche, come il tipo dei valori che deve avere ogni chiave. Utilizzando infine la funzione `mongoose.model("User", userSchema)` stiamo proprio legando il nostro Schema userSchema con il modello User, che ci permetterà di comunicare facilemente con MongoDB e avere anche tutta la struttura dei dati definita da userSchema. Inoltre è stato utilizzato un hook di mongoose, chiamato `prev`per capire se una password è stata modificato o meno, per applicare al momento giusto la cifratura della password tramite la funzione di bcrypt `hash`  
   - `user.controller.js`: le funzioni contenute in questo file sono quelle di login, di registrazione e di logout. Ognuna di queste funzioni segue uno schema molto simile, infatti in ogni file: scomponiamo la `req` inviata nel body della chiamata api per ricevere i dati ed estrarre quelli di interesse per la funzione che stiamo implementando. Tramite i dati ricavati, successivamente anche ad opportuni controlli, chiamiamo la funzione `User.findOne`, funzione di mongoose che ci permette di cercare all'interno del nostro DB tramite dei valori passati come parametro, come ad esempio l'email. Nel caso in cui stiamo registrando l'utente quello che facciamo è creare un nuovo modello chiamando `new User({})` e passando all'interno dell'oggetto i valori che abbiamo trovato nella richiesta per poi successivamente chiamare la funzione `User.save()` per salvare il nuovo utente direttamente sul DB . Infine restituiamo tramite la `res` delle varie risposte, che possono essere di conferma, mandando un status(200), o di errore, mandando status(400) o status(500) (dipende il tipo di errore). All'interno però della funzione di login, oltre a fare i controlli necessari e chiamando la funzione di bcrypt `compare` per comparare correttamente la password inviata con la password che abbiamo salvato sul db, facciamo anche un'altra cosa fondamentale, la creazione dell'accessToken. Chiamiamo infatti la funzione `token.js` descritta precedentemente mandando come parametro l'id dell'utente.
- `lobby.model.js e lobby.controller.js`: Questi due file sono molto simili a quelli analizzati sopra, quindi il file definisce il modello Lobby per la comunicazione con il DB e il file che definisce le funzioni che integrano il flow delle azioni da eseguire per le chiamate API che riguardano l'interazione con le lobby. Ci sono però delle differenze in alcune funzioni all'interno del controller che valgono la pena essere considerate: - `lobby.controller.js`: le funzioni, che definiscono le chiamate API che l'utente utilizza per comunicare con il server, contenute in questo file sono quelle di creazione, join, getter. Le funzioni sono molto simili a quelle già descritte in precedenza dello user.controller, troviamo infatti anche qui le funzione di find, in questo caso utilizziamo findById con l'id della lobby preso direttamente dalla richiesta con il comando `req.params.id` , la funzione di save quando creiamo una nuova lobby e altre funzioni conosciute per la manipolazione di array. Qui però troviamo anche un'altra cosa particolare: dopo aver salvato correttamente sul DB il cambiamento dell'array contenente gli id degli activePlayer, prendiamo dalla memoria globale della nostra app express il canale di comunicazione io, tramite il comando `req.app.get("io")`. Grazie quindi al canale e all'id della lobby in cui ci siamo uniti possiamo mandare un messaggio sul canale nella rooms privata. - `joinLobby`: in questa funzione c'è un passo fondamentale. Dopo aver aggiunto l'id dell'utente all'interno dell'array activePlayers, controllo se la lobby è piena. In questo caso infatti cambio lo status della lobby in "playing" (tutto questo fatto prima di salvare i cambiamenti sul DB per maggiore consistenza), e creo un array contente le informazioni sugli utenti appartenenti alla lobby in questione per creare un'oggetto da inserire in un registro, una mappa, che tiene conto delle partite in corso (così da non fare migliaia di chiamate al DB). Fatto questo comunico tramite il canale globale io, ma solo nella rooms con id uguale all'id della lobby, mandando a tutti un messaggio e anche l'array contente le informazioni dei giocatori - `lobby.model.js`: In breve, nel file ho definito le regole del tavolo, come il `starteBet` (puntata iniziale), il `numPlayers` (posti totali) e un array `activePlayers` che conterrà le chiavi (ID) degli utenti attualmente seduti, in modo da collegare il modello Lobby al modello User. - `deleteLobby`: In questo file però è presente anche una funzione che non è una API ma che lavora anche essa direttamente con il DB. Questa funzione infatti viene chiamata dal server stesso e serve per eliminare una lobby direttamente nel DB (e anche nel registro che teniamo nella RAM). - è bene aggiungere anche ulteriori spiegazioni su come adesso il tutto venga anche salvato in RAM per avere fin da subito un accesso rapido ad eventuali valori che potrebbero servire al server in base alle comunicazioni col il client. Infatti adesso non salvo più una partita in RAM solo quando la lobby si riempie ma lo faccio subito, aggiungendo tutte le informazioni necessarie all'array all'interno di un oggetto partita dei giocatori che man mano si collegano. Con questo approccio, chiamato RAM-FIRST, riesco anche a gestire al meglio la sincronizzazione con il DB, chiamandolo solo in casi di estremo bisogno, come il salvataggio dei dati relativi agli utenti sul DB per una corretta sincronizzazione.
- `game`: questa cartella contiene tutte le funzioni che gestiscono una partita appena avviata e la logica di gioco, e anche le strutture utilizzate per tenere traccia delle informazioni importanti. - `ActiveGame`: classe utilizzata per conservare le informazioni, i dati, di una partita appena avviata. Troviamo ad esempio il deck generato per la partita in questione, la gestione dei turni dei giocatori, l'array contente le informazioni sugli utenti, ecc... - `deck.js`: file in cui è presente la funzione di creazione di un array contenente degli oggetti, ognuno dei quali rappresenta una carta di un mazzo di carte siciliano. Inoltre il mazzo viene mischiato casualmente tramite l'algoritmo di fischer-yates. - `GameStateManager.js`: questo è il file in cui gestiamo il "registro" delle partite, tramite una hashMap e la funzione createNewGame. Questa funzione prende i dati salvati durante il login, dopo il controllo che la lobby si sia riempita, su tutti i dati importanti che il game deve avere, come le info sui giocatori e il deck appena creato. Inoltre troviamo anche la funzione getGame, che restituisce una partita con un id specifico se presente nel registro, e la funzione deleteGame, che elimina un game dal registro.
- `handlers`: in questa cartella troviamo gli handlers che gestiscono le comunicazioni tra server e client. - `registerGameHandlers`: qui troviamo tutti gli eventi sulla quale il server si pone in ascolto, sulla socket univoca che collega il server con un client specifico. Troviamo infatti, ad esempio: `socket.on("create_lobby"), socket.on("join_lobby_rooms")`, ecc... All'interno di queste chiamate poi comunichiamo tramite il canale io solo però alla rooms creata con l'id uguale a quello della lobby a cui i giocatori solo collegati. Ci sono da fare due menzioni importanti, che sono alla base della logica del gioco: - `join_lobby_rooms`: in questo evento troviamo un passo che vale la pane approfondire: controlliamo infatti se la partita è già iniziata o meno e nel caso fosse già cominciata (che significherebbe aver trovato la partita all'interno del registro) mandiamo nella socket del client il messaggio contente tutte le informazioni della partita, come ad esempio l'array contenente le informazioni principali dei giocatori connessi sulla lobby, l'id della partita e il valore dei soldi sul piatto di gioco. Questo controllo è fondamentale per evitare le race condition che si possono creare durante le molteplici chiamate tra client e server: se mandassimo direttamente il messaggio senza il controllo, potrebbe succedere che un client si unisse correttamente nella lobby ma senza ricevere il messaggio contenente le informazioni necessarie per la partita. -`player_draw`: Questo è l'evento che mandato dal client per richiedere al server di pescare una carta dal mazzo: è fondamentale infatti dividere sempre le responsabilità e non dare al client nessun "potere" sulla partita: tutti i controlli devono essere fatti lato server! Qui troviamo infatti la logica dietro la pescata: andiamo a riprendere il game dal nostro registro tramite l'id inviato dal client e dal game ci ritroviamo l'utente con il quale stiamo comunicando attraverso la socket. Dopo tutti i controlli preliminari gestiamo anche la logica per la "sconfitta", la perdita della puntata, e per la "vittoria", la vincita, in base alla carta pescata. Anche questa cosa deve essere fatta lato server perchè stiamo accedendo ad importanti campi, come ad esempio i soldi dell'utente, che devono essere modificati, e i soldi presenti sul piatto. Dopo aver fatto ciò mandiamo un messaggio di risposta al client, che intercetterà il messaggio perché lo mandiamo a tutti gli utenti collegati alla stessa rooms, quindi alla stessa lobby. - `player_bet`: Questo evento è molto simile al precedente: controlliamo infatti se la bet può essere fatta o meno controllando il balance (il saldo) dell'utente e controllando la quantità di moneta presente nel piatto: non possiamo infatti fare bet che superino il valore presente nel piatto.

### FRONTEND

- `types/index.ts`: Partendo dalle basi, in questo file troviamo tutte le interfacce che definiscono i tipi con la quale i nostri file lavorano. Questo è importante per sfruttare la forza di typescript: definire le strutture con le quali le nostre funzioni lavorano per sapere sempre le informazioni e i tipi con i quali si sta lavorando. Esempi di `interface` presenti in questo file sono: - `JwtPayload`: questa interfaccia definisce la struttura del token che prendiamo dal localstorage per autenticare le comunicazioni che avvengo sulla socket tra server e client. - `SocketJoinResponse`: interfaccia usata per ricevere i dati dal server a seguito di una richiesta di join in una lobby da parte del client. Dentro questa interfaccia definiamo infatti i tipi che devono avere i valori contenuti dentro l'oggetto risposta, ad esempio: message: string, giocatoriAlTavolo: Player[] (con `Player` interfaccia che definisce la struttura dei dati che caratterizzano un player in una lobby) ecc..
- `GameActions.ts`: In questo file troviamo semplicemente le funzioni utilizzati per gestire le mosse del giocatore durante la partita: il pescaggio della carta e la richiesta di mandare una bet. Queste due funzioni vengono chiamate al click dei rispettivi bottoni e l'unica cosa che fanno è emettere sulla socket l'evento corrispondente alla mossa inviata: `player_draw` se l'utente richiede di pescare una carta dal mazzo e `player_bet` se decide di mandare la bet. Queste due richieste saranno intercettate dal server più precisamente all'interno del `gam.handler.js` descritto precedentemente
- `hooks`: dentro questa cartella troviamo delle funzioni di estrema importanza che costituiscono il cervello di gioco sia per quanto riguarda la partita online che quella offline: - `useAuth.ts`: in questo custom hook si trova tutta la logica per gestire le varie funzioni e stati utili alla registrazione o al login di un utente. Troviamo infatti i vari useState che servono per salvare i dati mandati dal client nei vari form, dati che poi verranno mandati al server in base a quello che lo user ha richiesto. Troviamo infatti varie funzioni di handle per gestire: la funzione di login, la funzione di registrazione e anche la richiesta di un codice otp. Quando un utente vuole creare un profilo infatti deve prima verificare la validità dell'email, cosa che puà fare immettendo un codice otp che gli sarà mandato tramite l'email precedentemente inserita. Dopodiché potrà invece mandare, insieme al codice, anche lo username e la password dell'account - `useLobbies.ts`: custom hook che si occupa di tutta la logica utile alla pagina generale in cui l'utente controlla le lobby già attive o le crea tramite l'apposito form. Troviamo all'interno tutti gli useState utili che poi verranno esportati dal'hook per essere usati e renderizzati nella pagina. Troviamo inoltre le varie funzioni che gestiscono le diverse chiamate al server, come la creazione della lobby, o la funzione che serve a prendere le lobbies da DB e mostrarle all'utente. Questa funzione però non può essere gestita tramite una chiamata GET, perchè il client invia dei dati al server per personalizzare la chiamate e inserire dei filtri alla ricerca. Questo però va contro le regole https, che per una chiamata GET presuppongono la non presenza di dati nel body della richiesta, dati che cambierebbero l'esito della risposta. Per questo quindi il metodo di questa chiamata è una semplice POST. - `useGameEngine.ts`: Questa è una delle funzioni più importanti e che racchiude anche un concetto fondamentale in react: si tratta infatti di un `custom hook`, una funzione il quale nome comincia con `use` e che all'interno contiene degli hooks come `useState e useEffect`. Questi sono gli hooks più utilizzati e che ho utilizzato nel progetto in grande quantità. useState serve per definire uno stato privato all'interno di un componente, una funzione, tramite due valori restituiti come coppia di un array: `[element, setElement]`. Ho utilizzato questo hook ad esempio per definire il turno corrente della partita in corso, per salvare la socket da utilizzare nelle comunicazioni con il server, per salvare i cambiamenti al valore presente sul piatto. E' importante salvare queste informazioni con gli useState perché è l'unico modo per renderli "reattivi" ai cambiamenti e far vedere il cambiamento anche all'utente in maniera interattiva. Altro hook fondamentale è useEffect, che fa partire la funzione definita all'interno subito dopo che la funzione, o il componente in cui è definito, viene renderizzato nella pagina del client. Questo può quindi essere usato per far partire automaticamente delle chiamate API subito dopo essere entrati all'interno della pagina. Di fatti all'interno del nostro custom hook lo useEffect viene utilizzato per far partire subito la connessione con il server http, passo fondamentale per poter comunicare in maniera rapida e veloce tramite il canale io collegato con il server. Inoltre troviamo anche "le orecchie" in ascolto degli eventi mandati dal server, come ad esempio `new_card`, evento che manda al client la carta richiesta, e `new_game`, evento che invece racchiude tutte le informazioni della partita alla quale l'utente partecipa e che è appena iniziata. Infine, questo custom hook **restituisce** al file visivo solo le variabili essenziali (come l'array dei giocatori ruotato o il valore del piatto), nascondendo tutta la complessità dei calcoli. - `LocalGameEngine`: questa cartella racchiude tutti i file e il custom Hook per la gestione della partita offline. Troviamo infatti file come deck.ts, turn.ts e botDecision.ts che sono delle funzioni utilizzate poi nel file `useLocalGameEngine` per gestire correttamente tutto il flusso di gioco. -`useLocalGameEngine.ts`: custom hook molto simile a quello precedentemente analizzato. Questo hook contiene le chiamate a tutte le funzioni definite nei vari file, così da rendere il tutto più leggibile e facilmente modificabile per correzioni o aggiunte future. La funzione più importante chiamata in questo file, e anche quella più interessante da andare ad approfondire, è sicuramente il reducer, che altro non è che una funzione utilizzata come useState nel caso in cui la logica diventi molto complessa e difficile da racchiudere in poche righe. Questa funzione, che si trova nel file `localGameReducer.ts`, prende come input lo stato corrente della partita, che viene creato al momento della chiamata di questa funzione passando ad una funzione apposita lo username, la starteBet e il numero di giocatori, e il tipo di azione effettuata. Le azioni possibili sono PLAY_TURN e RESET_DECK: l'azione di giocata ad esempio eseguo il controllo della ammontare della bet, controlla la correttezza della puntata e fa pescare automaticamente una carta all'utente. Ricordiamo una importante differenza: quando tocca all'utente, e non ad un bot, non si verifica lo useEffect che parte appena cambia un turno, ritorna senza fare niente, ma viene chiamata una funzione che chiama direttamente la funzione con l'azione di PLAY_TURN.
- `components`: dentro questa cartella troviamo i così detti `components`, i componenti utilizzati da react per racchiudere un oggetto visivo da poter facilmente riutilizzare all'interno dei file per non scrivere più e più volte le stesse righe di codice. La forza però di questi componenti sta nell'usare le `props`. Grazie a queste props, che sono delle informazioni che noi passiamo al componente, riusciamo a sfruttare la struttura data dal nostro componente rendendola però unica. - `LobbyCard.tsx`: Questo componente viene utilizzato per creare le "card" che fanno vedere le lobby disponibili richieste dall'utente. Il concetto di props fa capire proprio come, lo stesso componente che da la stessa struttura visiva, può essere utilizzato per esporre informazioni diverse. Nel nostro caso infatti la card è la stessa, ma su di essa si vedono i diversi nomi delle lobby, il diverso numero dei partecipanti ecc.. Questo perché, quando renderizziamo i component per ogni lobby disponibile, passiamo ad ognuno di questi le props contenenti le informazioni di una lobby alla volta. Questo fa si che ogni card abbia informazioni diverse rispettando sempre la stessa struttura visiva, evitandoci di scrivere le stesse righe di codice per ogni lobby cambiando ogni volta solamente le informazioni caratteristiche di ogni lobby. Altra cosa fondamentale che troviamo dentro questo componente è la funzione `fetchJoinLobby`: questa funzione viene associata al bottone presente nella card che rappresenta la lobby e si occupa della chiamata API al server per la richiesta di join nella lobby. All'interno della fetch vera e propria inseriamo l'url per la chiamata API e passiamo nell'header della richiesta il token di autenticazione salvato nel localstorage del browser dell'utente, creato al momento del login. - `PlayerSeat.tsx`: Semplicemente il component utilizzato per renderizzare il posto nel tavolo di ogni utente, passando come props le informazioni dei giocatori. - `Navbar.tsx`: Questo component racchiude la logica che definisce la chat di gioco e anche il bottone per uscire dalla room. Come gli altri componenti utilizza useState per il mantenimento consistente dei dati e anche useEffect per gestire al meglio il cambiamento di stato quando cambiano i messaggi nella chat o quando si apre la chat. All'interno troviamo anche le funzioni fondamentali che fanno partire le chiamate alle funzioni dentro GameActions.ts per gestire: l'inoltro a tutti i giocatori della stessa lobby dei messaggi e anche il logout di un utente, con annessa terminazione della partita nel caso in cui restasse un solo utente nel tavolo
- `pages`: Cartella importantissima che contiene le differenti pagine nelle quali navighiamo durante la UX dell'utente, partendo dalla pagina di autenticazione fino al tavolo di gioco. Questa navigazione viene integrata grazie all'utilizzo dei `ReactRouter`, una libreria che mette a disposizione tutti gli strumenti necessari per la creazioni di differenti pagine che vengono renderizzate ad `uri` differenti. Non descrivo nel dettaglio le pagine perchè al loro interno troviamo semplicemente le componenti visive, gli oggetti tsx che vengono mostrati a schermo. La logica importante di ognuna di queste pagine si trova infatti nei corrispettivi custom hooks, come quello già descritto per la pagina del gioco, che si occupano di reagire ai cambiamenti degli stati interni, alle chiamate API verso il server e alla modifiche dei valori da passare poi alle componenti grafiche che importeranno questi valori
- `public`: In questa cartella troviamo tutti i file che devono essere comunicati subito al browser e che quest'ultimo può facilmente accedere quando viene inviata l'intera pagina dal server. Troviamo infatti una cartella contente tutte le immagini delle carte, che vanno messe qui perchè cambiano spesso durante la partita, ma soprattutto troviamo la gestione del `Service Worker` e del `manifest.manifestweb` che rendere la nostra applicazione web una PWA (progressive web app).
- `services`: In questa cartella troviamo delle funzioni molto utili in generale in tutto l''ambiente frontend, come la funzione che dato il token recupera l'id dell'utente associato a questo (`getIdFromToken.ts`) ma anche altre utilità, come - `CustomAlert.ts`: in questo file troviamo tutta la gestione dei custom alert gestiti tramite la libreria `sweetalert2`. In base a quello che deve essere mostrato in schermo sono stati definiti diversi tipi di alert, alcuni dei quali richiederanno anche un'interazione da parte dell'utente (banalmente gli alert dopo che un utente ha chiesto di voler uscire dal gioco che richiedono la conferma) - `fetchWithAuth.ts`: questa invece è una funzione fondamentale che gestisce tutte le fetch che vengono fatte dal client per comunicare con il server. Difatti, quando un utente fa partire una fetch dalla pagina generale in poi, tutte queste chiamate verranno gestite chiamando la funzione fetchWithAuth passando solamente l'url e un oggetto `options` dentro al quale si trovano dei dati richiesti per quella chiamata. Dentro però la funzione poi verrà controllato l'accesstoken salvato nel local storage, verrà inserito il metodo `headers` nell'oggetto e verrà quindi mandata la fetch completa. Nel caso però in cui la risposta del server mostrerà un problema con l'access token (problemi come invalidità o token scaduto), la funzione manderà una nuova fetch all'API di refresh inserendo nei metodi della richiesta anche `credentials:include`. Questo dirà al browser di prendere il `cookie http` e mandarlo al server. Dentro questo cookie infatti era stato salvato, al momento del login dell'utente, il refresh token, fondamentale per creare un nuovo access token da far utilizzare al client. Se il server risponderà senza problemi alla richiesta di refresh, manderà al client un nuovo token da utilizzare, e la funzione riproverà quindi la vecchia richiesta utilizzando per l'appunto il nuovo token. - `GameActions.ts`: dentro questo file invece troviamo una semplice oggetto con dei metodi funzione che gestiscono le mosse di gioco durante la partita. Queste infatti manderanno tramite la socket un messaggio al server tramite il canale bidirezionale instaurato dopo la connessione ad una lobby per comunicare le varie azioni da gioco.
